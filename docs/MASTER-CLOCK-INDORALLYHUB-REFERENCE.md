# Master Clock — IndoRallyHub UI Reference / Two-Repo Integration

Audit 2026-10-26; source: https://indorallyhub.id/ (via connected browser tab).

## What was actually verified on the external site
- Visible component called **Master Clock**; shows time with two fractional digits: HH:mm:ss.cc (example from tab: 09:03:27.44).
- Visible in both page/header and a second page position.
- The source webpage states it is an unofficial rally information hub.
- **NOT verified:** its source NTP clock, API, accuracy, timezone, backend algorithm, and whether its clock is generated by the client or server. Its apparent time cannot be adopted as official organizer time merely from the browser UI.

## NaviPRO adoption — proposed architecture, not code copied from the site
- Mirror the readable centisecond presentation and master/slave clock concept.
- Use one **NaviPRO-operated, authenticated time source** with server-issued Unix epoch milliseconds as the common reference for Navigator Page 1 and TSD Cadencer.
- Enforce \`Asia/Makassar\` WITA (UTC+08) for Buleleng; WIB (\`Asia/Jakarta\`) is one hour earlier.
- Implement client monotonic-time extrapolation and an uncertainty bound: server source uncertainty + at least half the request RTT. Reject untrusted, high-latency or stale time samples.
- Frontends must show \`UNSYNCED\` until a backend genuinely synchronizes to a documented NTP/GNSS source. Client header \`X-NaviPRO-Clock-Verified: 1\` is only meaningful on a trusted authenticated transport from a backend that monitors synchronization.
- Two decimal digits on screen are **display resolution**, not evidence of centisecond accuracy.
- **No 60:100 scaling**: one elapsed second always equals one second of cadence.
- NaviPRO Page 1 plans integer-minute sub windows and optional second-level CP/cue targets. Cadencer and NaviPRO use the same clock module and provenance.
- A scheduled sub change does not by itself prove a physical sub/CP boundary. Keep \`SCHEDULED_ONLY\` apart from reviewed activation.
- Historical Master Pos remains POST-EVENT evaluation data. Do not inject it into PREP timing tables.

## Proposed backend contract — NOT an IndoRallyHub endpoint

\`GET /api/master-clock\` with authenticated HTTPS, \`Cache-Control: no-store\`, and server-proven synchronization health.

\`\`\`json
{
  "serverEpochMs": 1792972800000,
  "sourceId": "NAVIPRO_MASTER_CLOCK",
  "sourceUncertaintyMs": 20,
  "sampleId": "illustrative-example-only",
  "timeZone": "Asia/Makassar"
}
\`\`\`

Header: \`X-NaviPRO-Clock-Verified: 1\` emitted only after server time-discipline verification. If unsynchronized, return non-success status and do not emit the verified header.

Samples are not implemented as a deployed API yet. Browser may display local time for reference, but must label it \`UNSYNCED\` and must not auto-activate schedule.

## Test and release gates
- \`node --test tests/contracts/master-clock.test.mjs\` (NaviPRO) or \`node --test tests/master-clock.test.mjs\` (Cadencer).
- Browser-rendering smoke test, two independent devices with deliberately skewed clocks, offline drift test, sleep/wake, genuine NTP/GNSS audit, real API authentication/CORS, and hardware/event clock comparison are still required.
- The supplied module and tests are contract prototypes, **NOT competition-ready timing**.
